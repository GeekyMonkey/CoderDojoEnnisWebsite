# Page and API access expectations

Updated 12 October 2026. This replaces the older 2025 analysis and its references to deleted page paths.

The [app feature contract](../app-features.md#roles-and-access) defines expected roles. `src/app/middleware/auth.global.ts` redirects unauthenticated navigation in `/mentor`, `/coder` and `/parent` to `/login`, restoring sessions on hard reload. It checks authentication, not current role authorization. `src/app/utils/memberNavigation.ts` filters menus using role metadata for presentation. Neither mechanism protects a server API or direct database access.

Login is `src/app/pages/(auth)/login.vue`; it calls the auth store and `/api/Auth/Login`, sets the returned Supabase session and navigates through `/logged_in`. NFC has a separate login API. Auth listener/store and session-recovery helpers handle initialization and expired sessions. F06 portal login history is restored through a service-only completion after session creation, independently of attendance; F07 complete-name matching now checks all first/surname splits alongside login/email candidates, validates passwords and orders candidates consistently (explicit login/email first, then stable IDs). F08 preserves the accepted four-character password minimum; its separate username-length question remains open. Hosted portal acceptance is unconfirmed.

Protected APIs derive a verified User account from the current Supabase user and stored account through `requestMember.ts`, then apply Mentor/Coder/Parent checks. Access to linked Coders is rechecked with `parentRequest.ts`. Profile, management, review, Coder and Parent APIs use narrow response/edit contracts. Controlled mutation RPCs are service-only and recheck the current actor/eligibility inside the transaction with concurrency safeguards. The Mentor-only pod realtime read helper separately verifies immutable auth identity and current role.

Expected database permissions must restrict private reads, prevent arbitrary client writes and keep credentials out of REST/realtime projections. The live metadata sweep found RLS disabled and broad grants on most tables (F01). It also found unguarded import, older attendance mutations and private lookup APIs (F02–F04). F03 is an accepted known vulnerability for the third-party hardware kiosk; F02 is deferred and F04 remains open, so the presence of guarded newer APIs must not be described as complete app-wide security.

Expected shared kiosk mode removes management authority and uses scoped device/sign-in access. Current mentor SignIn layout retains the mentor session (F12); the F03 hardware kiosk APIs retain their existing authorization behavior by explicit user decision. Their unauthenticated identifier-driven attendance writes and archived fingerprint lookup are a known accepted vulnerability; do not change these contracts as security remediation.

See the [final discrepancy list](../../openspec/changes/replicate-legacy-features/final-parity-discrepancies.md) for evidence, priorities and verification requirements. This documentation update did not execute exploit requests or modify live permissions/data.

The [proposed data-access design](../../openspec/changes/secure-role-based-data-access/design.md) covers all twelve tables, current-role identity bindings, controlled writes, public images and safe realtime invalidations. See the [table/field matrix](../../openspec/changes/secure-role-based-data-access/policy-matrix.md) and [verification matrix](../../openspec/changes/secure-role-based-data-access/verification-matrix.md). It is a proposal, not evidence that the policies are deployed.

F02 is explicitly deferred by the user until production cutover: keep the current legacy import unchanged during development/migration, then remove legacy import/read routes and decommission the old database after final reconciliation and dependency checks. This is a scheduled cutover action, not a resolved security finding.

The [F01 implementation branch record](../../openspec/changes/secure-role-based-data-access/implementation.md) documents the prepared policies, binding-based identity, private invalidations and validation. PR #57 is merged to develop and the F01 migration is applied to shared Supabase: 12/12 tables have RLS and protected grants, bindings and private invalidations are verified at database level. Successful hosted app deployment and end-to-end acceptance remain unconfirmed.

F04 is merged to develop: members/*, memberBelts/* and attendance SessionCurrent/SessionDate/SessionDateRange/SessionDates/SessionStats require a verified current Mentor before handlers run. Path case, encoded characters and trailing slashes are normalized for the guard. Non-Mentor own-profile Belt displays use scoped achievement APIs, and Parent linked-Coder/peer views keep scoped responses. The accepted F03 kiosk contracts are excluded. Hosted deployment and direct-request/UI acceptance remain pending.

F12 replaces shared mentor sign-in authority with a signed HttpOnly kiosk cookie (Secure in production, host-only, SameSite=Strict, /api/Kiosk path, current Dublin day and maximum 12-hour lifetime). Mentor-only Start registers the originating session UUID as revoked, revokes its Supabase refresh session and issues the bounded capability. Client auth, private query caches and channels are cleared before a hard replacement to /kiosk/sign-in. Dedicated kiosk endpoints validate signature/expiry/origin and expose only the scoped attendance welcome. The cookie cannot authenticate management or Supabase.

Protected API guards and coderdojo RLS reject the revoked JWT session ID even if the access token has not reached expiry. A new login gets a fresh session and restores normal role access. Registry/functions are service-only in the private schema; the migration is applied and rollback verification passed. No existing hardware endpoint or beta legacy redirect changed. Hosted Back/reload/multi-tab/expiry and full sign-out acceptance remain pending.
