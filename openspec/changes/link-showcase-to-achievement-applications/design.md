## Context
`AchievementApplicationForm` currently submits evidence notes through `useCoderActionsStore`, `/api/Coder/applications` and the atomic `coder_action` database function. Applications are records in `member_badges` and `member_belts`. `AchievementReviewsData` projects these records for coder and evaluator views. `ShowcaseCard` already supplies expandable project presentation, but its CSS currently lives in the public-area stylesheet.

## Decisions
- Add non-null `showcase_item_ids uuid[]` to both existing record tables, defaulting to an empty array. Use `showcaseItemIds` in client contracts. Do not create a join table or store copied project URLs.
- Extend application submission to accept the selected IDs alongside the existing notes. Existing callers omitting IDs resolve to an empty array. Keep the current 5–4000-character notes requirement and badge/belt progression rules.
- Keep selected IDs in the application form until submission. Add opens a picker backed by the own-member showcase TanStack store; exclude already attached IDs. Display selected entries with the common card and an external Delete/remove-link action. Canceling the picker leaves selection intact.
- Add a guarded pending-application link update, identifying the exact application record and achievement kind. Derive the actor from the verified coder session. Lock the application record, reject decided/other-owner records, compare the expected GUID array and change only `showcase_item_ids`. Use the existing coder action transaction pattern and preserve review/decision restrictions.
- Validate GUIDs and uniqueness in shared contracts and at the database write boundary. Newly added items must exist and belong to the application owner. Hidden items are valid evidence. Prune missing references before evaluating the requested selection; validate newly added IDs against existing owned entries. A missing old reference must not block removal of another link.
- Application submission and pending-link updates must remain atomic against concurrent mentor decisions and other coder edits. Duplicate submissions retain the existing pending record and must not silently overwrite its attachments; subsequent edits use the explicit guarded update.
- Extend review projections with IDs and resolved showcase card data, using batched lookups for all authorized applications. Do not use the public visible-only showcase list to resolve evidence. Evaluators see hidden linked items through their existing authorized review flow.
- Persist references, not snapshots: cards show current showcase details. Automatically remove missing IDs from stored application arrays; do not render unavailable-item markers. Removing an application link never invokes showcase deletion or storage cleanup. Reapplying after rejection creates a new record. User edits cannot change decided evidence, but automatic removal of missing showcase references also applies to historical/decided records.
- Move card presentation into the reusable component or a shared card stylesheet that works with both public and application themes. Leave grid/filter transitions in the public page. Provide an action slot outside the disclosure button for coder link removal; evaluators get read-only cards with description and external project link. Give each rendered card instance a unique disclosure ID, since the same project can occur in several application rows.
- Use TanStack store actions for selection data, submissions, attachment updates and review refresh. Reuse existing application-table invalidations; refresh linked card details when showcase entries change without losing unsaved selections.

## Migration and rollout
Deploy the additive empty-array columns and updated guarded database functions before dependent APIs. Update generated types, contracts, stores, shared card styling, application UI and evaluator views together. Existing applications with no showcase evidence behave as before.

## Self-healing references
- A showcase-delete trigger uses the deleted row’s `member_id` and `id` to remove that ID from the owning member’s `member_badges.showcase_item_ids` and `member_belts.showcase_item_ids` in the same transaction, preserving remaining IDs and their order. Match both `member_id = OLD.member_id` and array containment of `OLD.id`; leave other members’ applications untouched. This includes pending, awarded and rejected records.
- Add an initial migration cleanup for any pre-existing dangling IDs. Authorized application reads also repair dangling IDs as a fallback, covering older data or deletions that bypassed the normal trigger.
- Implement fallback repair as a database-side atomic prune against the current array, not a client read/replace operation, so it cannot overwrite concurrently added valid links. Preserve notes, dates, decisions and valid links. Empty results become an empty UUID array, never null.
- Automatic pruning is a narrowly scoped system action; it does not grant coders permission to edit decided applications. Reuse application-table invalidations so open coder/evaluator views refresh immediately after repair.
